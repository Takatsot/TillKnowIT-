1Welcome and ground rules

This app can change what every shop, supplier and school on the platform sees and is paid. Treat each action as one that someone else may later ask you to explain.

The Platform admin app is for members of the TillKnowIT platform team. Its seven sections cover the things that only the platform may do: define business types, set plans and ranking rules, approve suppliers, settle disputes, watch the money reconcile, run schools and the wallet, give partners read-only access to data, and keep the shared catalogue clean.

Four-eyes and audit

Two principles run through this manual.

  • Audit. The server writes an audit record for the admin actions described here (for example catalogue decisions and lookup changes). Your signed-in person id travels with each request. Assume that who did what, and when, can be looked up. Write notes as if a colleague, an auditor or a partner may read them.
  • Four-eyes. Money-moving and access-granting actions should be reviewed by a second person before or right after you do them. This is a process rule that the team follows. The app itself does not enforce a second approver. One signed-in admin can resolve a dispute, run payouts or issue a key alone. The four-eyes reviews are listed as a process item, not a software feature, in the project's status document. Agree who your second pair of eyes is, and use them for the actions marked below.

Because the app lets one person finish these actions alone, the safety comes from you. Before you resolve a dispute, resolve a reconciliation, run payouts, verify a school or give a partner a key, tell a colleague what you are about to do and why.

Which actions deserve a second person

Actions with money, access or reputation at stake

2Signing in and the menu

You sign in with your cell number and a code. There are no passwords to leak.

  1. Open the Platform admin app. In the Sign in box type your number under Your cell phone number.
  2. Tap Send me a code, then type the code under The code we sent you and tap Sign in.
  3. Your sign-in lasts 12 hours. Then the app says Your sign-in has run out. Please sign in again. Use Sign out when you finish or leave your desk.

Demo mode

In a demo or development version a Development only box shows the code on screen. The demo platform admin is Alice Admin, 082 555 0005. This never happens in the real service. Never use real shop or school data in a demo.

The menu

3Business packs

A pack is a business type made of features. Saving a change makes a new version, so tills know that their copy is out of date.

Open Business packs. The table has columns Pack, Code, Version, Features, Slip template, Status and Actions. A pack is Active or Switched off. Five packs are supplied: spaza, cafe, butchery, salon, and clothing and hardware.

Creating a pack

  1. Tap New pack.
  2. Fill in Pack code (lowercase letters, digits and underscores, 2 to 30 characters, starting with a letter; it cannot be changed later), Pack name, an optional Description (optional) and the Slip template code.
  3. Under Features this pack switches on tick the features it needs. The one for schools is School wallet (school_wallet), with the hint Turn on for shops that are school tuckshops.
  4. For a feature that takes settings, a box Settings for (feature) (JSON object, optional) appears. For example, the barcode rules for price_embedded_barcodes. The JSON must be a valid object.
  5. Tap Create pack. You see (Name) was created.

Editing, switching off and on

Tap Edit on a row to change it, then Save pack: (Name) was saved (version 3). Each edit raises the version. Use Switch off and Switch on to retire or restore a pack. Use Cancel to leave a form without saving.

Edits reach every shop that uses the pack, the next time their tills sync. Check the JSON settings twice: a wrong barcode rule changes what every till in that business type does. The default pack can never be switched off; the server refuses.

A brand-new pack works with no code change, so a new business type is a data task, not a release. Test it on a demo shop first.

4Plans and billing

Plans decide what a shop or supplier pays each month and which features and limits they get.

The screen opens with a standing warning: These prices are placeholders. The seeded plans were made before the pilot pricing decision, so check every price before a business is charged. The free message bundle is also a placeholder. The real billing gateway that charges a card is not connected yet.

Open Plans and billing. The heading is Plans. Use Show plans for to filter by Everyone, Shops or Suppliers. The columns are Plan, Code, For, Price a month, Features and Actions. A free plan shows Free; a feature with a limit shows (feature) (up to 50).

Note the line Only plans that are switched on are listed here, because the server's plan list shows only those. A plan you switch off will disappear from this list. There is no switch-off button here; to retire a plan, untick Offered to customers when editing. Remember that you will then not see it again in the app.

Making or changing a plan

  1. Tap New plan or Edit.
  2. Enter Plan code (lowercase letters, digits and underscores; fixed once saved), Who it is for and Plan name.
  3. Enter Price a month (rand), for example 199 or 199.50. A bad value gives Write the price in rand, for example 199 or 199.50.
  4. Tick Offered to customers if it may be chosen.
  5. Under Features on this plan tick features; for a feature with a limit, fill Limit for (feature). Leave empty for no limit. A limit is a whole number, 0 or more.
  6. Tap Save plan. You see (Name) was saved.

A price change affects what businesses are billed. Have a second person confirm the amount in rand, not cents, before you save. Never lower a limit below what existing customers already use without warning them.

5Suppliers and ranking settings

Suppliers join the marketplace only after a person at TillKnowIT has checked them. This section also holds the numbers that decide how offers are ranked.

Suppliers waiting for approval

Open Suppliers. The first card, Suppliers waiting for approval, has columns Supplier, Status, Areas, Terms (for example Minimum order R300, delivery R40, pays on delivery) and Actions. When none are waiting: No suppliers are waiting for approval.

  1. Tap Review on a supplier. The panel Review (name) opens.
  2. Check each item under What you checked (all four are needed to verify): Business registration checked, Contact person confirmed, Delivery capability confirmed and Prices reviewed. Tick a box only after you have really done that check, outside the app.
  3. Tap Verify supplier: (Name) was verified.
  4. Or write a clear Reason for rejecting (the hint says The supplier is told this reason) and tap Reject supplier: (Name) was rejected.
  5. Close the panel without a decision.

The four ticks are your declaration that you did the checks. A second person should spot-check registration documents and bank details. The rejection reason goes to the supplier: keep it factual and courteous.

Marketplace ranking settings

The card Marketplace ranking settings decides how offers are ranked for shops. A change applies to the next ranking and needs no release. A value outside the allowed range is refused. The table shows Setting, Value, Allowed range and Used when not set.

The five ranking settings
SettingEffect
Weight of costHow much the true cost per unit counts in the ranking.
Weight of supplier ratingHow much the average delivery rating counts. A supplier average counts only after 3 ratings.
Weight of delivery timeHow much speed counts.
Sponsored boost (%)How much a sponsored offer is lifted. It is always labelled sponsored.
VAT used to compare prices (%)The VAT rate used so that prices with and without VAT can be compared.

Change a value, then tap Save (setting): (Setting) was saved. A non-number gives Write a number. A number out of range gives Allowed range is (min) to (max).

Ranking is a matter of trust. The marketplace is built so that, with default settings, a sponsored offer never outranks a cheaper non-sponsored one. Raising the sponsored boost, or lowering the weight of cost, can change that. Do not change these numbers without a second person agreeing and writing down why.

6Disputes and payments

When a shop and a supplier disagree about an order, the money for that order is frozen until you decide. This is a serious duty.

Open disputes

Open Disputes and payments. The first card, Open disputes, lists disputes with Raised, Raised by, Order, Reason, Status and Actions. If there are none: There are no open disputes.

  1. Read the reason, and look at the order and what both sides say, outside this app if you must.
  2. Tap Resolve. The card Resolve the dispute on order (n) opens.
  3. Under Outcome choose Pay the supplier or Refund the shop. The hint says: Paying the supplier releases the held money. Refunding the shop does not release any of it.
  4. Add a Note (optional). Make it a habit to always write one: what you saw, and why.
  5. Tap Resolve dispute. You see The dispute on order (n) was resolved. Use Close to back out.

Releasing money cannot be undone from this app. Have a second person read the facts and agree the outcome before you tap Resolve dispute.

Payment reconciliation (supplier payments)

The card Payment reconciliation compares the payment partner's records with ours for one day. A daily job does this to the cent as well; here you can run it for a chosen day.

  1. Choose the Day and tap Run reconciliation. The button says Running... while it works.
  2. Read Report for (day): (n) payments matched. then either Nothing is out of step for this day. or (n) do not match.
  3. For each mismatch the table gives Partner reference, Kind and Detail. Take the reference to the payment partner and find out what happened.

This section only shows the mismatches. A mismatch has no "resolve" button here: you fix it with the partner and your finance colleague. The wallet's own reconciliation, described in the next chapter, is different and does block payouts.

Real payment partner: only a development fake is connected today. Reports here reflect the fake partner. Do not treat a clean report as proof about real money until a real partner is live.

7Schools and wallet

A school wallet holds children's money. This is the most sensitive part of the platform: take care with names, cards and cash.

Open Schools and wallet. The card Open a school lets you pick one: Pick a school from the list to work on it. A school you register on the School tab opens by itself. Under School choose Choose a school and tap Open school. You see Working on (name).

The sections are tabs, labelled School, Holders, Breaks and menu, Cash and staff accounts, Payouts and Reconciliation. Holders, Breaks and menu, and Cash and staff accounts need an open school (Open or register a school first.); Payouts and Reconciliation do not.

The School tab: register and verify

  1. Under Register a school type the School name, an optional EMIS number (optional), and the Tuckshop id.
  2. The tuckshop must already exist, and it must be verified before the school can be (see the field agent manual). Tap Register school: (Name) was registered. The school then shows Waiting for verification.
  3. Check the school and its tuckshop. Tap Verify school: (Name) was verified. Statuses are Waiting for verification, Verified and Suspended.

The details card shows Platform fee and Payouts (the schedule). Under Settings:

  • Platform fee (percent): from 0 to 10. Only the platform can change it. For example 2.5.
  • Payout schedule: Daily, Weekly or Monthly. Weekly pays on Friday; monthly on the last day of the month.
  • Teachers may use monthly staff accounts: lets teachers run a monthly tab.
  • Daily ceiling per wallet (rand, optional): R0 to R5000; empty is no ceiling. The parent's own limit also applies, and the lower one wins.
  • Offline split time (minutes): from 5 minutes to 8 hours (480).

Tap Save settings: The settings were saved. Under School admins enter a Person id and tap Add admin. The person must already have signed up. A school admin looks after holders, breaks and the menu.

The fee is deducted from every wallet sale before the shop is paid. Verifying a school and setting its fee are decisions to share with a second person.

The Holders tab: learners and teachers

A holder is a learner or teacher with a wallet. The table lists Name, Type, Grade, Class, Status and Actions.

Add one person

Under Add one learner or teacher give the First name, Surname, the type (Learner or Teacher) and, for learners, the grade and class. Tap Add person: (Name) was added. followed by Link code: and the code. Edit later with Edit (Change (name)) and Save changes.

Import from a file

  1. Under Import holders from a file read the hint: a CSV or Excel file with a first name column and a surname column. Sending the same file again creates nobody twice.
  2. Choose the File and tap Import holders (it says Importing...).
  3. Read the summary: (n) created, (n) already there, (n) not valid. The table Rows that were not created lists each bad row with Row, Outcome and Detail. Fix the file and import again; duplicates are flagged, not repeated.
  4. The card Link codes appears with the warning: Link codes are shown once. Save them now and give each to the school so parents can link their child. Tap Save link codes (CSV) straight away.

Link codes are shown once. If you close the page without saving them you cannot get them back from this screen. Handle the file as private: it contains a code for every child. Give it only to the school, never to a group chat, and delete your copy afterwards.

Photos, where used, are stored encrypted and served only to a till of that school.

Cards and wristbands

Tap Cards on a holder: the card Cards and wristbands for (name) opens. Type the Card number (tap a card on a reader that types its number, or read the printed number). Add an optional Card name that the parent sees, for example Blue wristband. Tap Link card: The card is now linked to (name). Each card is Active or Blocked; Block stops it at every till: The card is blocked.

A block reaches tills at their next snapshot. A parent who reports a lost card should be told this. A replacement card links to the same wallet.

The Breaks and menu tab

Pre-orders close at each break's cut-off time. A school has at most 10 breaks, and saving replaces the whole list. For each break enter Break code, Break name and Cut-off (HH:mm) (South African time). Use Add a break and Remove break (n), then Save breaks: The breaks were saved.

Under Menu items the table shows Item, Price and Available (Yes/No). Use Add a menu item or Edit: Item name, Price (rand) (for example 12.50), optional Product id (optional) and Category code (optional), and Available to order. Tap Save item. Pre-order prices come from this menu, and parents' category and item blocks use these codes.

The Cash and staff accounts tab

Record a cash deposit is for cash the school paid into our account so it can be loaded onto wallets. Enter Amount (rand) and a Deposit reference, then tap Record deposit: The deposit of R500,00 was recorded. In this model, the school owes that cash until it is paid in.

Record the amount exactly as banked, with the bank's reference. A deposit loads real wallets. Have your second person compare the bank statement with the entry.

Staff accounts show what teachers owe the tuckshop for a month. Enter the Month as 2026-10 and tap Show month. You see Total owed for (month): (amount) and a table of Teacher and Owed. Tap Settle (month): (Month) was settled. Settling posts once per teacher and month; settling the same month again does not charge twice.

The Payouts tab

Run payouts pays each tuckshop what it is owed from wallet sales. Payouts are normally driven by each school's schedule; here you can run them for an optional Day (optional). A payout is made once per shop per day, and a failed one is recorded and retried. Tap Run payouts.

  • If a reconciliation difference is unresolved you see Payouts are on hold: (reason) and nothing is paid.
  • If nothing was owed: Nothing was owed, so no payouts were made.
  • Otherwise a table lists Shop, Day, Amount, Status and Error.

The card A tuckshop's wallet sales and payouts takes a Shop id and a From/To date, and Show sales gives Wallet sales, Platform fees, Paid out and Still owed to the shop. Use it to answer a shop owner's question before you re-run anything.

Running payouts moves real money to shops once a real partner is live. It is safe to repeat (the partner reference is the idempotency key, so a day is not paid twice) but not safe to run blindly. Check the blocked message and have a second person approve the run.

The Reconciliation tab

The wallet reconciliation compares what the payment partner holds with our ledger for a day, to the cent, and checks that every ledger transaction balances. A job does this daily; you can run it for a day. Every run is recorded and listed.

Each run shows Partner holds, Our ledger says and Difference, with a status: Matched, Does not match or Resolved.

A reconciliation difference blocks all wallet payouts until it is resolved. Resolving means writing, in plain words, what was found and what was done: What was found and what was done, at least 5 characters (the hint says so, and the button stays grey until you meet it). Write a real explanation, not "ok". A second person must read it before it is saved. The note is the only record that explains why money was allowed to move again.

  1. Pick the Day and tap Run reconciliation.
  2. For a Does not match run, find the cause with the finance team and the partner. Do not guess.
  3. Tap Resolve on the run, type the note, and tap Resolve again. You see The reconciliation for (day) was resolved.

The wallet's money records (the double-entry ledger) are append-only. Nothing here edits history; a correction is written as a new entry through the proper route, never by changing old ones.

Stored-value partner: only a development fake is connected today. Top-ups, refunds on leaving and payouts have been coded and tested against fakes only. The wallet's separate database and service are prepared but are infrastructure work still to do.

8Partner API

A partner (a bank, a bookkeeper, an app) reads shop data through a read-only API. It sees only shops that approved it.

Open Partner API. The card API clients lists each Partner, Key starts with (the first characters of its key), May read (its scopes), Calls a minute, Status (Active or Revoked) and Actions.

Scopes

A scope is one kind of data a partner may read. Today there are two: Daily sales (sales.daily) and Monthly sales (sales.monthly). Choose the narrowest set the partner needs. The API is read-only.

Registering a partner

  1. In Register a partner type the Partner name and an optional Contact email (optional).
  2. Under What the partner may read tick at least one scope (Choose at least one.).
  3. Set the Rate limit (calls a minute), from 1 to 6000. Bad values give The rate limit is a whole number from 1 to 6000.
  4. Tap Register partner: (Name) was registered. Copy the key below now.
  5. The card New key for (name) shows the API key. Tap Copy key. If copying fails, select it and copy by hand.
  6. Only after you have stored the key somewhere safe, tap I have copied the key.

The key is shown once and cannot be shown again. Only a fingerprint is kept on our side. If you lose it, you must rotate the key. Pass it to the partner over a safe channel, never by plain email or WhatsApp.

Rotating a key

Tap Rotate key on a partner. A new key is shown once, in the same way. The old key keeps working for 24 hours, so the partner can switch without a gap. Rotate on a schedule, and at once if a key may have leaked. If a leak is suspected, rotate and then consider revoking.

Revoking a partner

Tap Revoke. To avoid mistakes the app asks again with a button Revoke (name) for good; Keep backs out. Afterwards: (Name) was revoked. The partner's status becomes Revoked.

Each shop owner approves each partner for their own shop and may withdraw. Your key alone gives a partner no shop data. Every call a partner makes is logged. The rate limit is counted in memory per server, so with several API servers the real limit is higher than the number you set.

9Catalogue approvals and lookups

The shared catalogue is the list of products every shop can look up by barcode. Keeping it clean helps every shop.

Suggested products

Open Catalogue. The card Suggested products lists products that shops suggested which are not in the shared catalogue yet: Barcode, Name, Size, Category, Suggested and Actions. If none: No suggested products are waiting for review. You have three choices for each one.

Approve

  1. Tap Approve. The panel Approve (name) opens with the hint Change a field only if the shop got it wrong. Empty fields stay as suggested.
  2. Tidy the Name, Size or Category, or tick Keep the suggested category.
  3. Tap Approve product: (Name) was approved.

Reject

Tap Reject, enter a Reason for rejecting (the server requires one), and tap Reject product: (Name) was rejected.

Merge

Use Merge when the product already exists in the catalogue under another record, for example a duplicate with a typing error.

  1. Tap Merge. The panel Merge (name) into an existing product opens.
  2. Type the Barcode of the product we already have and tap Find product. You see Found: (name) ((barcode)). Check that it is the right product.
  3. Tap Merge into this product: (Name) was merged. The shops that suggested it move onto the approved product.

A merge moves shops' products to the target product. Look at the found name and barcode before you confirm. If you merge into the wrong product, many shops are affected and there is no undo button in this app. Every decision is audited.

Platform lookups and translations

The card Platform lookups holds the lists the apps use. Switching one off hides it from new choices. Choose a list under List:

The table shows Code, Order and Status (On or Off). To change one, tap Edit (Edit (code)); to make one, tap Add to this list. Enter the Code (lowercase letters, digits and underscores), the English name and the Sort order, tick Switched on if it should be offered, then tap Save: (Code) was saved.

Lookups support translations on the server, and the changes are audited. In this screen you enter the English name. First drafts of some translations exist for isiZulu, isiXhosa, Sesotho, Setswana and Afrikaans, written without first-language speakers: they are not reviewed and should be checked by a speaker before release.

Never delete or recode a lookup that shops already use. Switch it off instead. A code cannot be reused for something different without confusing the data already saved with it.

10What is not connected or not built

Be honest with colleagues and partners about the state of things. According to the project's status document:

  • Payment partner (suppliers). Only a development fake exists. Held money, disputes, signed webhooks and the daily reconciliation are built and tested, not run against a real partner.
  • Stored-value wallet partner. Only a development fake exists. Top-ups, refunds on leaving and payouts are coded and tested without a real partner.
  • Billing gateway. The real charger is not connected. Plan prices and the free message bundle are placeholders until the pilot pricing decision.
  • Sign-in SMS. Built for BulkSMS, never run against the live service. Anyone can ask a code for any number (five per hour per number), so a per-address limit is needed before launch.
  • Four-eyes reviews. A process item, not enforced by the app (see chapter 1).
  • Partner API. Version 1 runs inside the main host; the separate host and gateway are not built. The rate limit is per server in memory. A security review is outstanding. The penetration test is a to-do.
  • Plans screen. It shows only active plans and has no "switch off" button.
  • Translations. Drafts are unreviewed; most back-office and admin areas show English only.
  • Un-doing. This app has no undo for merges, dispute outcomes, reconciliation resolutions or key revocations.

11Words used in this manual

Pack
A business type made of features (spaza, cafe, butchery and so on), versioned each time it changes.
Feature flag
A named switch (such as school_wallet) that turns a part of the till or back office on.
Plan
A monthly price with features and limits, for shops or suppliers.
Ranking
How the marketplace orders supplier offers for a shop.
Dispute
A shop and supplier disagreement over an order, which freezes the held money.
Reconciliation
Comparing our records with the payment partner's, to the cent, for a day.
Ledger
The append-only, double-entry record of all wallet money. Balances are calculated from it, never stored.
Holder
A learner or teacher who has a school wallet.
Link code
A one-time code that lets a parent link a child. Shown once.
Payout
Money sent to a tuckshop for its wallet sales, after the platform fee.
Scope
A kind of data a partner key may read (sales.daily, sales.monthly).
Rotation
Replacing a key with a new one; the old key works for 24 more hours.
Idempotent
Safe to repeat: the same request is never done twice.
Four-eyes
A rule that a second person reviews an important action.
Audit
A permanent record of who did what and when.
Lookup
A managed list the apps use, such as categories, units or municipalities.
Merge
Moving shops from a suggested product to an already approved one.
