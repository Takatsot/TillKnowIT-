2Run it on your PC

You need the .NET 10 SDK, Node.js 22 and SQL Server. SQL Server LocalDB comes with Visual Studio and is enough.

The API

  1. Open a terminal in backend/src/Host/TillKnowIT.Api.
  2. Set the environment and the database, then run. In Git Bash: 
    ASPNETCORE_ENVIRONMENT=Development \
ConnectionStrings__Database='Server=(localdb)\MSSQLLocalDB;Database=tillknowit_dev;Trusted_Connection=True;TrustServerCertificate=True' \
dotnet run --no-launch-profile --urls http://localhost:5080
  3. The first start creates the tables and seeds one person for every role, a shop with a till and ten products, a supplier, and a school with a linked child. A file called dev-seed.md beside the API lists the phones, PINs and the till's setup code. It is ignored by git.
  4. Check it is alive: http://localhost:5080/api/v1/health should answer.

If you start the API without ConnectionStrings__Database it uses a default string that points at another server and fails. Always set it.

The apps

  1. In frontend/ run npm ci once.
  2. Start an app with npm run dev -w @tillknowit/<app>, for example @tillknowit/back-office. Each dev server forwards /api/v1 to the API on port 5080.

4Settings that matter

Development fills in safe defaults. Outside Development the API refuses to start without the keys below, which is deliberate. Set them as environment variables (a double underscore stands for a colon) or in a secrets store, never in the repository.

SettingWhat it is
ConnectionStrings:DatabaseThe SQL Server connection. ConnectionStrings:Wallet optionally gives the wallet a database of its own.
Auth:RequiredSet to true in every real environment. Every request that names an acting person must then carry that person's token.
Auth:TokenKeySigns sessions. At least 32 characters.
Storage:Root, Storage:KeyWhere encrypted documents live, and the 32-byte base64 key that encrypts them.
Slips:BaseUrl, Slips:SigningKeyThe public address of the slip page and the 32-byte base64 key that signs slip links.
Wallet:QrKey, Wallet:AllowanceKeySign the rotating payment QR and the offline allowance. At least 32 characters each and different from one another.
Wallet:WebhookSecrets:*, Payments:WebhookSecrets:*One secret per partner, used to check signed callbacks.
Cors:OriginsThe addresses of apps hosted elsewhere (for example the GitHub Pages address, without a path or trailing slash).
Sms:BulkSms:TokenId, TokenSecretBulkSMS credentials. Without them SMS, and so sign-in codes, fail visibly outside Development.
Accounting:*Token key, return address and the Xero and Sage client details, in both the API and the worker.
Demo:EnabledSeeds demo data, uses fake partners and shows sign-in codes on screen. Never on where real data lives.

Generate a 32-byte base64 key with, for example, openssl rand -base64 32.

6A free public demo

For showing TillKnowIT to people with made-up data. It is not for real shops: free hosting sleeps, has small limits and has no backups you can count on.

PartWhereCost
The seven appsGitHub Pages, published by .github/workflows/pages.ymlFree for a public repository.
The APIA Render web service described by render.yaml and backend/DockerfileFree; sleeps after about 15 idle minutes, so the first request takes up to a minute.
The databaseA hosted SQL Server database (next chapter)The one part with no free option outside Azure, and the Azure free offer is not available on every subscription.

1. Publish the apps

  1. On GitHub open Settings → Pages and set Source to GitHub Actions. This is done once. Without it a publish fails with "Failed to create deployment (404)".
  2. Push to main, or run the workflow Publish the apps to GitHub Pages by hand. Each app is built for its own path, for example /till/ and /back-office/.
  3. The apps appear on one site with a landing page that links to each app and lists the demo people.

The build bakes in the API's address. It uses the repository variable API_URL if there is one, and otherwise https://tillknowit-api.onrender.com. Without a working API address, sign-in shows "This copy of the app has no server connected yet".

2. Publish the API

  1. On render.com choose New → Blueprint and pick the repository. Render reads render.yaml.
  2. When asked, paste ConnectionStrings__Database (never commit it). The other keys are generated.
  3. Keep the service name tillknowit-api, or change Slips__BaseUrl and the apps' API_URL to match.
  4. The first start creates the tables and the demo people, which takes a few minutes.

The demo settings show every sign-in code on screen. Anyone who knows a phone number can sign in as that person. Use made-up data only.

7The database on Azure

TillKnowIT runs on SQL Server, so a hosted database must be SQL Server. Neon, Supabase and PlanetScale are PostgreSQL or MySQL; moving to them would mean redoing every module's migrations and retesting everything.

  1. In the Azure portal create a SQL Database with a new server and SQL authentication. Look for the Apply offer banner on the Basics tab: it is the free database, and it is not offered on every subscription.
  2. If there is no free offer, choose General Purpose, Serverless with a small maximum size (the preview prices storage per gigabyte, so 2 GB costs a few cents a month) and turn on auto-pause. Compute is charged only while the database is awake. Check the cost summary before you create it.
  3. Under the server's Networking add a firewall rule. Render's addresses are not Azure's, so Allow Azure services is not enough for a demo; a wide rule works for made-up data and should be removed or narrowed before anything real goes in.
  4. Copy the ADO.NET connection string and add Connection Timeout=60; so a paused database has time to wake.

Keep the admin password out of the repository and out of chat. If it has been shared, reset it from the server's Overview page and update the connection string in the host's settings.

8Before real shops use it

Replace demo mode with real settings: an always-on API and database with backups, the SMS provider, Demo:Enabled off, Auth:Required on, a limit on sign-up requests per address (today there is a limit of five codes an hour per phone number, but not per address, so bulk SMS cost is open to abuse), and the reviews below.

To run it

  1. Run the API and worker against a real SQL Server and confirm migrations apply, the seed loads, the outbox claim query works, cascade paths are accepted and the insight aggregate constraint is accepted.
  2. Run the offline sync spike from decision record 0001 before building the local database and selling screen.
  3. Turn on Auth:Required, set Auth:TokenKey, connect the SMS provider.

Partners and accounts

  • Payment partner, stored-value (wallet) partner, WhatsApp, SMS and email providers, and an airtime and electricity partner.
  • The real billing charger. Pricing: the seeded plan prices and the free message bundle are placeholders until the pilot pricing decision.
  • A registered credit provider and a written agreement for pay-later, with their sandbox.
  • Xero and Sage developer accounts and OAuth apps, then one connection and one day's journal tried in each sandbox.
  • A secrets store (Key Vault) for accounting tokens and partner secrets.

Reviews

  • Legal and data-ethics review of market insights and pay-later sharing (POPIA, competition rules), before any shop is asked to opt in.
  • Penetration test; load test at 10,000 shops and 2 million sales a day; review of the partner API, whose rate limit is in memory per server and needs a shared counter behind several servers.
  • First-language speakers to write and review the translations.

Still to build

  • Real printer, drawer, scale and kitchen-screen adapters once devices are chosen.
  • Offline sync of stock transfers; lay-by deposits and tips in the accounting journal; suggested replacement (M3-3); automatic weekly top-up (W2-5).
  • The separate Insights service and Partner API host, if scale asks for them.

9Problems and fixes

You seeCause and fix
"The server answered 405" or "This copy of the app has no server connected yet" on a hosted appThe app was published without the API's address, so it called its own host. Set the API_URL repository variable (or deploy the API at the default address) and publish again.
The API fails at start with a missing keyOutside Development every key in chapter 4 is required. The message names the one that is missing.
The API cannot reach the databaseCheck the connection string, and for Azure SQL the firewall rule. The error "Client with IP address … is not allowed to access the server" means the caller's address is not allowed.
Sign-in works on a PC but not hostedAdd the apps' address to Cors:Origins (scheme and host only, no path or trailing slash).
No sign-in code arrivesOutside Development and demo, a real SMS provider is required. Five codes an hour are allowed per phone number.
A till will not accept its setup codeThe code works once. Reset the till's credential from the owner's Staff and tills screen and approve it again.
Azure CLI fails on a company network with a certificate or timeout errorThe network inspects or blocks the sign-in traffic. Use the Azure portal in the browser instead; do not switch certificate checking off on a company machine.
The Docker image does not build on RenderThe build log says why. The image has not been built on the machine it was written on; the same publish step and settings were run as a plain process in Production mode.
